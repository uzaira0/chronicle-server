# Translating Chronicle server messages

The server generates a small amount of text that a participant or researcher reads on screen:
API error bodies, enrollment and participant-link rejections, validation messages, and the one
reminder title the backend generates for mobile notifications. All of it lives in a single
message table.

## For a translator

1. Copy `src/main/resources/messages.properties` to `src/main/resources/messages_<lang>.properties`.
   For Spanish that is `messages_es.properties`. For a region-specific variant, add the country:
   `messages_es_MX.properties`.
2. Translate the **values only**. Never change a key (the part left of `=`).
3. Keep every `{0}`, `{1}` placeholder, and keep them meaning the same thing. They are substituted
   at runtime with an error id, a count, a parameter name, and so on. Reordering them within a
   sentence is fine; deleting one is not.
4. In a line that contains a `{0}` placeholder, a literal apostrophe must be doubled (`''`) —
   `java.text.MessageFormat` treats a single `'` as quoting. Lines with no placeholder need no
   escaping.
5. Files are read as UTF-8; accented characters can be typed directly, no `\uXXXX` escapes needed.
6. A key you leave out falls back to the English text, so a partial translation is safe to ship.

## How a language gets selected

`ChronicleServerMvcPod.localeResolver()` registers Spring's `AcceptHeaderLocaleResolver` with a
default of `en`. For each request:

- The client's `Accept-Language` header picks the table — `Accept-Language: es` selects
  `messages_es.properties`, `es-MX` prefers `messages_es_MX.properties` and falls back to
  `messages_es.properties`.
- No header, or a language with no table, resolves to `messages.properties` (English). The JVM's
  own host locale is deliberately never consulted (`setFallbackToSystemLocale(false)`), so a
  server running under a non-English system locale still answers in English by default.

Callers resolve text through `com.openlattice.chronicle.i18n.Messages`:

- `Messages.get(key)` / `Messages.format(key, args…)` — request locale, via `LocaleContextHolder`.
- `Messages.get(key, request)` — for servlet filters, which run before the `DispatcherServlet`
  resolves a locale; the locale comes from `HttpServletRequest.getLocale()`.
- `Messages.en(key)` — forces English, used where a string is written to the audit trail.

Adding a message: add the key to `messages.properties`, then call one of the above. A key that is
missing everywhere resolves to the key itself rather than failing the request.

## What is deliberately not translatable

- Anything a researcher typed: study titles and descriptions, policy and consent text,
  questionnaire and survey text, reminder titles configured on a study, notes.
- Field names, enum values, ids, CSV/Excel export headers (they are field names, not prose) and
  URL paths — clients parse these.
- Log lines and audit-trail descriptions. The audit trail is single-language by design; where a
  string is used for both an audit record and a response, the audit record uses `Messages.en`.
- Protocol-level security rejections that never reach a screen: request-signature and replay
  checks (`MobileApiSignatureFilter`), CORS origin rejection, JWT revocation, request-URI and
  parameter-pollution hardening, SSRF blocks, metrics-endpoint auth. Several of these strings also
  double as internal control-flow values.
- `src/main/resources/webapp/index.html`, a static one-line deployment placeholder page.

## Verifying nothing is hardcoded

`ast-grep scan src/main` (rule `server-i18n-response-literal` in `lint/i18n/`, also run by the
monorepo `make i18n-lint`) fails on a literal string, or `"literal" + expr`, passed to
`ResponseStatusException`, `response.sendError`, `reject(...)`, a `ResponseEntity` constructor or
`.body(...)`, or the `message =` argument of `ApiError` (its `error` argument is the HTTP reason
phrase and is not matched). It matches by node shape, so comments and line breaks inside the call
do not hide it. The two request-hardening filters listed above are excluded by exact path; any
other protocol-only rejection can carry `// ast-grep-ignore: server-i18n-response-literal` (or a
bare `// ast-grep-ignore`) on its own line directly above. Trailing text after the rule id breaks
the suppression and a same-line trailing comment is not consulted.

Proof: `lint/i18n/cases/` is a table-driven suite (`FIRE: rule-id` markers must produce exactly
those findings; the excluded filter paths, `src/test`, and every suppression form are exercised).
`scripts/i18n-lint-selftest.sh` runs it; the monorepo `scripts/i18n-lint-mutation.sh` also plants
a violation under `src/main`, checks the scan fails naming it, and removes it.

Known holes, on purpose: `"$detail"` alone, `IllegalStateException`/`require` text (developer
diagnostics), and audit-log strings.

Verified with ast-grep 0.42.1.

**Standard alternative for later.** Spring's `ResponseEntityExceptionHandler` resolves
`problemDetail.title.<FQCN>` / `problemDetail.<FQCN>` codes through the `MessageSource` for
any `ErrorResponse` / `ErrorResponseException`, which is the RFC 9457 (Problem Details) shape:
a machine-readable `type` and status plus a localized `detail`. `ResponseStatusException`
reasons are not resolved that way, which is why responses go through `Messages.get` today. If
the API moves to Problem Details, those codes replace the explicit lookups.
